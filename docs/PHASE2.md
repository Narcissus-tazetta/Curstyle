# Phase 2 互換性・安全性(macOS 27.2 / arm64)

Phase 1 のエンジンに足した機能の仕様と、実機で確かめた結果。

## 追加した CLI

```
curstyle report [file]               診断レポートを書き出す(既定 ./curstyle-report-<日時>.txt、- で標準出力)
curstyle make-theme <dir> [--labels] テスト画像を theme.json + PNG で書き出す
```

### 診断レポート

不具合報告にそのまま添付できるテキスト。次を含む。

- OS バージョンとビルド番号、機種(`hw.model` / `hw.machine`)
- `diagnose` の全項目
- `com.apple.universalaccess` のうち `cursor` を含むキーの生の値(色・サイズ)
- 使う非公開シンボルごとの所在イメージ、または欠落
- `CGSCursorNameForSystemCursor` の表と、macOS 27.2 の固定表との差分
- 53件の名前ごとの状態・ハッシュ・size / hotspot / フレーム数 / 画像寸法
- ジャーナルの中身、スナップショットの件数と取得時の環境

ホームディレクトリのパスは `~` に置き換え、ユーザー名を含めない。

### 番号入りテーマ(`make-theme --labels`)

`arrow` / `ibeam` はテスト画像、`cursor.2〜43`(欠番の 6 を除く)は番号を描いた 32pt の四角(hotspot は中心)。標準画像が同一の 7/8・9/10 は片方(7・9)だけを定義し、別名処理でもう片方にも当たるかを同時に確かめる。`CursorTheme.write(directory:)` で書き出し、`apply <dir>` の読み込み経路をそのまま通す。

## ポインター色のカスタマイズ中の扱い

`cursorIsCustomized=1` のとき:

| 操作 | 動作 |
| --- | --- |
| `apply` / `snapshot` | 拒否(何も登録せず、スナップショットもジャーナルも変えない) |
| `reset-system` | 拒否 |
| `restore` | 実行する(どんな状態でも標準へ戻す経路は塞がない。表示は変わらない) |
| `diagnose` | 「問題」として報告し、終了コード 1。`ArrowS` / `IBeamS` が「不明」になるのは想定どおりと説明する |

`apply` を拒否する理由(実測):

1. 登録は成功し読み戻しも一致するが、画面は利用者が選んだ色のカーソルのまま変わらない。
2. 適用前のスナップショット更新で、システムが登録した色付きの画像を「標準」として取り込んでしまう。
3. 色をリセットすると、システム(AccessibilityFoundation)が `ArrowS` / `IBeamS` を登録し直し、`cursor.13` を削除するので、テーマはどのみち消える。

色をリセットした直後は `ArrowS` / `IBeamS` が「色リセット直後の標準」に変わり、`cursor.13` が未登録になる。`diagnose` では `ArrowS` / `IBeamS` が「不明」と出るので、`curstyle snapshot` で取り直す(次の `apply` でも自動で取り込まれる)。

### スクリーンショットの十字が変わらない理由

`/usr/sbin/screencapture` は `CGSRegisterCursorWithImages` と `CoreCursorSet` を自分で呼び、`CoordinateCursor` というクラスを持つ(シンボルと文字列で確認)。座標つきの十字を自前で描き、独自の名前で登録していると見られる。システムの名前は上書きしない(上の試験でテーマが残った)。アプリ独自のカーソルとして、変えられないものに分類する。登録している名前そのものは確かめていない。

## 安定性の測定: テーマ切替の繰り返し(2026-11-09)

`make-theme`(3件)をテーマ A、`make-theme --labels`(41件)をテーマ B として、release ビルドの CLI で「`apply A` → `apply B` → `restore`」を自動で繰り返した。各 `restore` の後に `status` で全件が「標準(スナップショット一致)」かを確かめ、WindowServer の RSS(`ps`)と phys footprint(`top` の MEM。root なしで読める)を記録した。`footprint` / `vmmap` は root が要るため使っていない。

| 回数 | 失敗 | `restore` 後に標準でない名前 | 所要時間(中央値 / 最大) |
| --- | --- | --- | --- |
| 100回(操作300回) | 0 | 毎回0件 | apply A 272ms / 469ms、apply B 318ms / 401ms、restore 176ms / 204ms |
| 300回(操作900回、540秒) | 0 | 毎回0件 | apply A 249ms / 348ms、apply B 291ms / 429ms、restore 142ms / 180ms |

WindowServer のメモリ:

- footprint は 300回の前後とも 725M。途中は 661M〜735M の範囲で上下しただけで、増え続けてはいない。
- RSS は 300回で 150.5MB → 157.3MB と単調に増えた(1回あたり約23KB)。ただし、切替を止めて同じ長さ(9分)放置しただけでも 157.3MB → 161.5MB 増えた。放置中の footprint も 666M〜752M の範囲で揺れた。測定中はほかの操作も行われうる状態だった。
- 結論: 切替によるリークの証拠はない。ただし RSS の揺れが大きいので、1回あたり数十KB以下のリークまでは否定できない。

この測定は読み戻しだけで判定しており、ループ中の画面表示は目視で確かめていない。終了後は `diagnose` で 53件すべて標準、ジャーナルも clean だった。

## 安定性の測定: 再ログイン(2026-11-09)

番号入りテーマ(`make-theme --labels`、43件)を適用した状態で再ログインした。記録は `.build/measure-A/`(git 管理外)。

| 段階 | 読み戻し | 目視 |
| --- | --- | --- |
| 再ログイン前に apply | 43件一致 | 番号入りに変わった |
| 再ログイン直後 | テーマは全件消えた。ArrowS / IBeamS は再ログイン前のスナップショットと別の標準(ArrowS: hot 4.5,4 → 5,5、IBeamS: size 22x23 → 23x22・hot 11.5,11 → 12,11。PHASE0 と同じ差)。cursor.N は 40件が未登録に戻った | 標準に戻った |
| 再ログイン後に apply | 43件一致。スナップショットは再ログイン後の標準に取り直された | 番号入りに変わった |
| その後 restore | 53件が標準(スナップショット一致)。ArrowS / IBeamS は再ログイン直後のハッシュに戻った。ジャーナルは clean | 標準に戻った |

分かった問題:

- 再ログイン直後の `diagnose` は、未登録に戻った cursor.N を「不明」と警告していた。cursor.N の未登録は正常なので、状態「未登録(アプリが使うときに OS が標準を登録する)」として警告しなくなった(再起動・サイズ変更でも同じ)。新しい標準になった ArrowS / IBeamS は、他のカーソルアプリによる書き換えと区別できないため、まだ「不明」として警告する。
- テーマが消えているのにジャーナルが `applied` のまま [OK] と出ていた。ジャーナルが適用中なのにテーマの画像が登録されていない名前があれば、「テーマが消えている」と警告する。
- この状態で `restore` すると、再ログイン前の標準(hotspot の違う ArrowS / IBeamS)で上書きする(未修正)。ログイン後の再適用(Phase 3)は、スナップショットの取り直しを先に行う必要がある。

番号入りテーマ(43件)を適用した状態で再起動した。記録は `.build/measure-A/pre-restart/` と `post-restart/`(git 管理外)。

| 段階 | 読み戻し | 目視 |
| --- | --- | --- |
| 再起動後 | テーマは全件消えた。ArrowS / IBeamS は再起動前の標準と同じハッシュ(再ログインのときのような別の標準にはならない)。cursor.N は 39件が未登録(cursor.13 / cursor.31 だけ標準が登録済み)。ジャーナルは `applied` のまま [OK] | 標準に戻った |
| 再起動後に apply | 43件一致 | 番号入りに変わった |
| その後 restore | 53件が標準。ジャーナルは clean | 標準に戻った |

再起動後の `diagnose` は、再ログイン直後と同じく未登録の cursor.N を「不明」として警告し、終了コード 1 を返した(正常な状態の誤警告。上の修正で解消)。

## 安定性の測定: スリープ復帰(2026-11-09)

番号入りテーマを適用した状態でスリープし、復帰した。復帰後も `status` は43件が適用中で、画面も番号入りのままだった。この最初のスリープは、種別(ディスプレイ / システム)を `pmset` のログから特定できなかった。

蓋を閉じるシステムスリープでも測り直した(外部ディスプレイを外した状態、AC 電源)。`pmset` のログで `Clamshell Sleep` に入り、約12秒後に `Wake from Deep Idle` で復帰したことを確かめた。復帰後も `status` はテーマ適用中43件・標準10件で適用直後と同じ、ジャーナルは `applied` のままで、画面も番号入りのままだった。12秒より長いスリープ(ディープスリープの深い段階、ハイバネート)は試していない。

## 安定性の測定: ポインターサイズの変更(2026-11-09)

番号入りテーマ(43件)を適用した状態で、アクセシビリティのポインターサイズを 1 → 4 に変えた(`CGSGetCursorScale` も 1.0 → 4.0)。

| 段階 | 読み戻し | 目視 |
| --- | --- | --- |
| サイズ変更直後 | cursor.N 41件が未登録に戻り、ArrowS / IBeamS の2件だけテーマが残った | 矢印と I ビームだけ番号入り。ほかは標準 |
| サイズ 4 のまま apply | 43件一致。`apply` は拒否されない | 番号入りに変わり、サイズ 4 の大きさも維持された |
| サイズ 4 のまま restore | 53件が標準。ジャーナルは clean | 標準に戻った(サイズ 4 の標準) |
| サイズを 1 に戻す | ArrowS / IBeamS は標準のまま。cursor.29 / cursor.39 が未登録になった。ジャーナルは clean | 標準 |

サイズ変更でも OS がカーソルを登録解除してテーマが消えるが、ポインター色と違い、`apply` / `restore` はサイズ変更中でも正しく働く。拒否する必要はない。

## 安定性の測定: 外部ディスプレイ(2026-11-09)

内蔵ディスプレイ(Retina 2560x1664)と外部ディスプレイ(1920x1080、非 Retina、ミラーなし)を接続した状態で、番号入りテーマ(43件)を適用した。読み戻しは43件一致。両方の画面で矢印・I ビーム・リンク上の指差しなどが番号入りになり、問題は見られなかった。`restore` 後は53件が標準で、ジャーナルは clean、両方の画面で標準に戻った。ディスプレイの抜き差し中の挙動と、Retina と非 Retina でのぼやけ・大きさの差は個別には記録していない。

## 確かめていないこと

- 番号入りテーマで、どの操作にどの番号が出たか。表示が変わったことは確かめたが、`CursorCatalog.roleNames` の対応表と一致するかは記録していない。
- 縦書きの I ビーム、表のセル、ズームイン/アウトなど、上で試していない操作の cursor.N(AppKit への問い合わせで番号は分かっているが、表示は目視していない)。
- 長時間のスリープ(ハイバネートを含む)からの復帰、ディスプレイの抜き差し中、ユーザー切替。
- 他のカーソルアプリとの競合(手元に無い)。診断は「スナップショットとも適用内容とも違う名前」を不明として出すだけで、原因のアプリは特定しない。
