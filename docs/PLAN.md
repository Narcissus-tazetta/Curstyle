# Curstyle 開発計画

macOS のシステムカーソルをテーマ単位で差し替える、軽量で長期安定するアプリ。Windows のカーソルテーマ変更に近い操作感と、配布されているアニメーションテーマの取り込みを目指す。

## 「長期安定」の定義(最初に決める)

非公開 API に依存する限り、「Apple が OS を更新しても必ず動く」とは保証できない。保証できるのは次の4点であり、この計画はこの4点を満たすことを「長期安定」と定義する。

1. **壊さない**: どんな失敗でも、利用者のカーソルが壊れた(赤い四角、全部が矢印になる等)まま残らない。常に標準へ戻せる。
2. **壊れたら気づく**: 適用後に読み戻して検証し、反映されていなければ検知して利用者に伝える。黙って質が落ちない。
3. **壊れ方が小さい**: OS が変わっても、全滅ではなく「未知の識別子だけ標準のまま」のように縮退する。
4. **直せる**: 新しい OS(beta 含む)が出たら早期に検知し、修正して配布する運用を持つ。

保証できないこと: Apple が API を削除・変更した場合の無停止動作、macOS の将来バージョンでの完全な動作、全アプリでの反映(アプリ独自のカーソル指定は上書きできない)。

## 過去の故障の実績(調査済み、2026-11-08)

3つの既存アプリの Issue を読んだ結果。**API のシンボルが消えて壊れた例は見つからず、壊れ方の大半は「データ・状態・タイミング」だった。**

| 故障 | 事例 | 設計への反映 |
| --- | --- | --- |
| 新 OS で識別子が増え、一部だけ反映される | Mousecape #287(macOS 26 で `ArrowS`/`IBeamS`/`cursor.26`/`cursor.20` が必要) | 識別子を固定表にせず、実行時に列挙する(下記) |
| 適用が再起動後に消える | Mousecape #278 | ログイン時の再適用をヘルパーで確実に行い、結果を検証する |
| 復元・削除後も赤い四角が残る | Mousecape #309、#253 | 適用前のスナップショットを保存し、復元は専用の経路で行う。復元の検証を必須にする |
| アクセシビリティのポインター設定が優先され、テーマが消える | MaCursor #21(macOS 27 beta、ポインターの色の「リセット」で復旧) | 競合する設定を診断で検知し、利用者に伝える |
| アニメが静止中に止まる / スクリーンショットで崩れる / arm64 ビルドで動かない | Mousecape #215、#204、#225 | アニメ関連は実機の受け入れテストに含める |
| 画面の端でしか反映されない | MaCursor #30、Mousecape-swiftUI #33(原因未確定) | 手元で再現するか Phase 0 で確認。再現・原因特定できるまで対策を足さない |
| 本家の保守停止 | Mousecape 本家は 2024-07 が最終コミット | 単独メンテナへの依存を避け、自前で追従できる体制にする |

## 手元で確認できた事実

- macOS 27.2 / arm64 に、必要な非公開シンボルが**存在する**(`dlsym` で確認のみ、呼び出しは未実施): `CGSMainConnectionID`、`CGSRegisterCursorWithImages`、`CGSCopyRegisteredCursorImages`、`CGSSetSystemDefinedCursor`、`CoreCursorUnregisterAll`、`CoreCursorSet`、`CoreCursorCopyImages`、`CGSSetDockCursorOverride`、`CGSGetCursorScale`、`CGSSetCursorScale`、`CGSCursorNameForSystemCursor` ほか。
- 上記のうち `CoreCursor*` は ApplicationServices 側にあり、CoreGraphics 単体には無い。リンク先を間違えると見つからない。
- `CGSCursorNameForSystemCursor(id)` で ID(既存ツールは 0〜127 を走査)から識別子名を引ける。新 OS の識別子の自動発見に使える見込み(実行して確認するのは Phase 0)。

## 目的と完了条件

- 目的: Arrow / IBeam / PointingHand をはじめとするシステムカーソルを、静止画・アニメーションともに差し替え・復元できる独立エンジンを作る。UI は後。
- 最初のマイルストーン(Phase 0〜2)の完了条件:
  - CLI から Arrow・IBeam・Link を変更し、標準に戻せる(手元 macOS 27.2 / Apple Silicon で再現)
  - 適用結果を読み戻して検証でき、各識別子の成否をログで追える
  - 不正なテーマを渡しても既存状態が壊れず、全カーソルを標準に戻せる
- 製品化(Phase 5)の完了条件: 「安定性の合格基準」の表を満たし、下の運用体制が動いていること。

## 方針(ユーザー決定済み)

- UI は編集機能まで作る(テーマ一覧・プレビュー・取り込み・フレーム速度と hotspot の編集・メニューバー・診断レポート書き出し)。ただし順序はエンジン → ログイン時の自動再適用(Phase 3) → UI。
- 当面の使い手は自分だけ。署名・公証・DMG・自動更新は後回しにし、公開を決めた時点で行う。
- 既存アプリのコードは書き写さない。読むのは公開されている関数シグネチャと挙動に限り、実装は自分の設計と実測で書く(クリーンルーム)。
- 配布は Developer ID 署名 + 公証 + GitHub Releases。Mac App Store は対象外。SIP 無効化・システムファイル書き換え・WindowServer へのコード注入はしない。
- 取り込み形式: Windows `.cur` / `.ani`、Mousecape `.cape`、アニメーション GIF。内部形式は独自で、インポータは別モジュール。
- **独自の API / 経路を作ってもよい(ユーザー許可)**。ただし本線に載せるのは Phase 0 の実測で得た根拠がある場合に限る(下記バックエンド階層)。

## バックエンド階層

`CursorBackend` プロトコルの背後に複数の実装を置き、診断で使えるものを選ぶ。

| 階層 | 内容 | 位置づけ |
| --- | --- | --- |
| A: `CGSBackend` | 非公開 CGS/CoreCursor API(3 実装と同じ経路) | 本線。Phase 1 で実装 |
| B: `OverlayBackend` | システムカーソルを隠し、透明な最前面ウィンドウに自前のカーソルを描画してマウス位置に追従させる | 退避経路。A が使えない OS の暫定対応として実装する(ユーザー決定)。公開 API 中心だが、ハードウェアカーソルを全アプリで隠すには非公開呼び出しが必要になる可能性が高い(未確認)。描画が1フレーム遅れる、フルスクリーンやセキュア入力で出ない恐れがある。Phase 3 の後、UI の前に作り、まず実現性(隠せるか・遅延・フルスクリーン)を測る |
| C: WindowServer 直接通信 | CGS の内部プロトコルを自前で再実装 | 研究ブランチのみ。結局同じ OS 内部機構に依存するため、本線には載せない。A でも B でも解決できない具体的な故障が出た場合だけ深掘りする |

## 安定性のための設計原則

1. **識別子を固定表にしない**: 起動時に `CGSCursorNameForSystemCursor` で ID を列挙し、各識別子の標準画像を `CoreCursorCopyImages` / `CGSCopyRegisteredCursorImages` で取得する。画像が同一のもの(別名)はピクセルのハッシュで検出し、テーマの定義が1つでも別名すべてに適用する。固定表は初期値と、動的発見との差分検知にだけ使う。新 OS で識別子が増えても全滅せず、増えた分は標準のままになるだけ、という縮退にする。
2. **適用はトランザクション**: 適用前に現在の登録内容を保存 → 全識別子へ登録 → 読み戻して検証 → 1つでも失敗したら保存した状態へロールバック。
3. **復元の独立経路**: 標準復元は、テーマ適用のコードとは別の最小の経路にする(`CoreCursorUnregisterAll` + 検証)。復元専用の CLI コマンドも持ち、アプリが起動しなくても使える。
4. **ガードつきの再適用**: 再適用はイベント駆動(ログイン・スリープ復帰・ディスプレイ変更・ユーザー切替)のみ。debounce と回数上限を持ち、上限を超えたら止めて利用者に通知する。ポーリングはしない。
5. **起動時の自己診断**: OS バージョン、必要シンボルの存在、読み戻しの一致、競合する設定(アクセシビリティのポインター色・サイズ、他のカーソルアプリ)を確認し、結果を診断レポートに出す。問題があれば利用者に分かる形で表示する。
6. **シンボル解決は `dlsym`**: 欠落時にクラッシュせず「この OS では未対応」と診断を出して無効化する。無効化したことは必ず利用者に伝える。
7. **画像はすべて自前で検証**: サイズ・フレーム数(1〜24)・hotspot・色空間を適用前に検査する。範囲外は拒否。

## 運用体制(これが無いと長期安定は成立しない)

- macOS の beta が出たら、その日に手元で受け入れテストを回す(beta 用の別ボリュームまたは別機材を用意する)。
- 受け入れテストは、スクリプト化された「適用 → 読み戻し → 復元 → 読み戻し」を CLI で自動実行し、OS 差を即座に検知できるようにする。表示そのものの確認は目視を含む手動テストが必要(GUI セッションを持たない CI では判定できない見込み。未確認)。
- 不具合報告のために、診断レポート(OS・シンボル・識別子の一覧・読み戻し結果・競合設定)を1コマンドで書き出せるようにする。
- 修正版の配布経路(自動更新)を Phase 5 までに用意する。
- 保守が続けられなくなった場合に備え、仕様と診断手順を文書化して残す。

## 確かめていない前提

- 上記シンボルを**実際に呼んで**正しく動くか(存在確認のみ。引数・戻り値・副作用は未実測)。
- `CGSCursorNameForSystemCursor` の列挙が macOS 27.2 で全識別子を返すか。
- 読み戻し(`CGSCopyRegisteredCursorImages`)が「登録されたこと」の確かな証拠になるか。登録成功でも画面に出ないケースがあるかもしれない。
- 「画面の端でしか出ない」現象の原因。ご相談メモの「画面収録中は正常」は一次情報で確認できていない。
- `OverlayBackend` でハードウェアカーソルを全アプリで隠せるか、遅延が許容範囲か。
- Developer ID 配布時の非公開 API 利用が Apple の規約・公証で問題にならないか。公開前に規約を確認する。
- 手元は macOS 27.2 のみ。macOS 26 の実機・複数ディスプレイ環境は未確保。

## アーキテクチャ(案)

```
Curstyle.app (SwiftUI, 後回し)
   │
CurstyleHelper (SMAppService のログイン項目、イベント駆動)
   │
CursorKit (Swift Package)
 ├─ CursorTheme / CursorCatalog : 実行時発見した識別子・別名グループ
 ├─ ThemeValidator              : 画像・hotspot・フレーム数の事前検証
 ├─ CursorBackend (protocol)    : apply / restoreDefaults / diagnose
 │    ├─ CGSBackend             : 非公開 API 呼び出し (C ブリッジ、dlsym)
 │    └─ OverlayBackend         : 退避経路 (研究後に判断)
 ├─ Snapshot / Recovery         : 適用前保存・ロールバック・独立した復元
 ├─ Diagnostics                 : 自己診断・レポート書き出し
 └─ Importers (別ターゲット)    : cur / ani / cape / gif → CursorTheme
curstyle CLI : 適用・復元・診断・受け入れテスト
```

`ApplyReport` は識別子ごとの登録結果・読み戻し一致・再試行有無・未確認項目を持つ。登録 API の成功と、画面に正しいカーソルが出ていることは区別して扱う。

## 手順

### Phase 0: 実測(最優先)
結果は `docs/PHASE0.md`。識別子の自動発見・復元経路・読み戻し検証の前提がいくつか外れたため、Phase 1 はそちらの申し送りを優先する。

1. Swift Package + C ブリッジを作り、シンボルを `dlsym` で解決して、`CGSCursorNameForSystemCursor` の列挙結果を取得する。
2. Arrow 1つを差し替え・読み戻し・復元・読み戻しして、各 API の戻り値を記録する。
3. 識別子の別名グループ(ピクセルハッシュ)を作り、macOS 27.2 の実態と既存アプリの固定表の差を確認する。
4. 「画面の端でしか出ない」現象が手元で再現するか確認する。再現しなければ記録に残す。
5. アクセシビリティのポインター色・サイズを変えた状態で、反映がどう変わるか確認する。

### Phase 1: エンジン本体
仕様と実機の結果は `docs/PHASE1.md`。

- `CGSBackend`、`CursorCatalog`、`Snapshot` / `Recovery`、トランザクション適用を実装。
- アニメ(複数フレーム + 間隔)と HiDPI(1x / 2x)を扱う。
- スナップショットなしで OS の標準へ戻す `reset-system`(ポインター色リセット時のシステムの再登録と同じ処理)。

### Phase 2: 互換性・安全性
結果は `docs/PHASE2.md`。
- 不正テーマの拒否、部分失敗時のロールバック、競合検知、診断レポート。
- 安定性測定(テーマ切替の繰り返し・再ログイン・再起動・スリープ・ポインターサイズ・外部ディスプレイ)は完了。結果は `docs/PHASE2.md`。

### Phase 3: 自動復旧ヘルパー
結果は `docs/PHASE3.md`。LaunchAgent(`curstyle helper install`)として常駐し、再ログイン・再起動・ポインター設定の変更でテーマが消えたら入れ直す。UI を作る Phase 5 で SMAppService に置き換える。
- イベント駆動の再適用(debounce・回数上限・失敗通知つき)。
- 再適用は「スナップショット取り直し → 適用」の順にする(再ログイン直後は標準の ArrowS / IBeamS が変わるため)。

### Phase 3.5: OverlayBackend
- `CursorBackend` の第2実装。実現性の測定から始める。

### Phase 4: 長期安定性テスト
- 主要アプリ(Safari / Chrome / Terminal / Excel / VS Code / Finder)での表示確認、複数ディスプレイ・Retina・拡大率、アニメ(静止中・スクリーンショット時)、72時間常駐、スリープ復帰30回、テーマ切替100回。

### Phase 5: 製品化
- インポータ、テーマ一覧とプレビュー、フレーム速度・hotspot 編集、メニューバー、ログイン時起動、診断レポート書き出し。
- 公開を決めたら DMG・公証・自動更新を足す。

## 検証方法

- テストが通るだけでは「効いた」とはみなさない。毎回、実機で実際にカーソルが変わったことを目視と読み戻しで確認する。
- 画面収録では判定しない(収録中だけ挙動が変わる報告があるため)。

| テスト | 合格基準(目標値、未測定) |
| --- | --- |
| 通常のマウス移動 | 追加の表示遅延・ちらつきを視認できない |
| アイドル CPU | 平均 0.5% 未満 |
| 常駐メモリ | 50MB 未満 |
| 長期稼働 | 72時間、エンジン起因のクラッシュなし |
| スリープ復帰 | 30回連続で復帰後の状態が正常 |
| テーマ切替 | 100回連続で変更・復元に成功 |
| 異常なテーマ | 安全に拒否し、既存状態を維持 |
| 標準への復元 | 失敗注入(途中で強制終了)後も復元コマンドで必ず標準に戻る |
| 未知の識別子 | 識別子を意図的に欠落させても縮退し、診断に出る |
| OS 互換性 | macOS 27(手元)で合格。26 と beta は機材確保後 |

## うまくいかなかった場合

- Phase 0 で呼び出しが失敗する・反映されない場合: 進めず、原因を特定する(MaCursor の 27 対応との差を読む)。
- 「端でしか出ない」現象が OS 起因で回避不能と分かった場合: 既知の制約として文書化し、診断レポートで利用者に伝える。無制限の再適用で隠さない。
- 復元できなくなる変更は入れない。最終手段は再ログイン。
- 新 OS で `CGSBackend` が動かなくなった場合: 診断で無効化を通知し、`OverlayBackend` が実用なら切り替え、そうでなければ標準カーソルに戻して「この OS は未対応」と伝える。
- エンジン単体で既存アプリ以上の安定性が出ないと測定で分かった場合は、MaCursor への貢献に方針転換する。

## 検討して捨てた案

- 「確実に壊れない」と約束する: 非公開 API では不可能。代わりに上記4点を定義した。
- WindowServer 通信の自作を本線にする: 同じ OS 内部機構に依存し、安定性が上がる根拠がない。研究ブランチに留める。
- MaCursor のコードをフォーク・流用する: GPL-3.0 が派生物に及ぶ。
- 識別子の固定表を保守し続ける: macOS 26 で実際に壊れた原因そのもの。
- 不具合ごとに強制再登録を足す: 原因の切り分けを妨げ、CPU とちらつきの原因になる。
- ポーリングで状態監視する: 軽量性に反する。
- Trails / Shaker / Translator / Gestures などの周辺機能: エンジンの安定性が先。
- SIP 無効化・コード注入: 通常の利用者が使えなくなる。
